# 점수 API 버전 기록·복구·성능 확인

이슈 #9의 API·PostgreSQL·Redis를 연결한 최종 검증 방법입니다. 저장한 점수의 계산 근거를 추적할 수 있는지, 서버가 둘이어도 거래가 중복되지 않는지, 캐시 장애 후 같은 계산으로 돌아오는지 확인합니다.

## 어떤 버전을 남기나

| 버전 | 실제 값과 의미 | 저장 위치 |
| --- | --- | --- |
| 모델 | 모델 파일 전체의 SHA-256. 전처리기·군집·분류기·판단 기준이 들어 있는 파일을 식별 | API 응답과 DB `result.model_version` |
| 피처 | 현재 `1`. 직전 1시간·7일 건수와 평균·표준편차 계산 규칙을 식별 | API 응답·DB `result.features.feature_version`·Redis 상태 |
| 정책 | 현재 `fixed-threshold-v1`. 저장 모델의 고정 기준 이상인지 확인하는 방식 | API 응답과 DB `result.policy_version` |
| 캐시 형식 | 현재 `snapshot_version=1`. Redis에서 이력을 읽는 형식을 식별 | Redis 상태 |

모델 파일이 달라지면 해시도 달라집니다. 피처 계산이나 판단 규칙의 의미를 바꾸면 해당 버전 상수도 올려야 합니다. 금액 기준값 자체는 응답의 `threshold`에도 남습니다. 같은 거래 재요청은 현재 모델로 다시 계산하지 않고 DB에 남은 최초 응답·버전을 반환합니다. 피처 버전이 맞지 않는 캐시는 DB에서 다시 구성합니다.

## 복구 기준과 확인 범위

PostgreSQL 기록이 확정 기준입니다. Redis는 DB 저장 후 갱신하며 두 저장소의 동시 저장을 가정하지 않습니다. 전체 카드를 먼저 불러오지 않고 신규 거래가 들어온 카드부터 복구합니다.

| 상황 | 처리 | 검증 근거 |
| --- | --- | --- |
| 같은 ID 동시 요청 | 최초 거래 한 건과 응답만 유지 | 자동 테스트와 실제 HTTP 서버 두 개에 동시 8회 전송 |
| 같은 ID의 내용 변경 | 409 반환 | 자동 테스트와 실제 HTTP |
| 모델·INSERT·COMMIT 실패 | DB 기록 취소, 새 캐시 발행 없음 | 실제 DB 오류를 발생시키는 자동 테스트 |
| DB 확정 후 Redis 쓰기 실패 | 저장된 응답 반환, 다음 신규 거래에서 복구 | Redis 쓰기 오류를 발생시키는 자동 테스트 |
| Redis 접속 불가 | DB로 계산·저장 | 자동 테스트와 접속 불가 주소로 실행한 실제 HTTP 서버 |
| API 재시작 | 최초 응답 유지 | 별도 서버 프로세스 종료·재실행 후 HTTP 비교 |
| 캐시 유실·손상·구버전 | DB의 직전 거래로 재구성 | 자동 테스트. 유실은 실제 HTTP에서도 확인 |
| DB 장애 | 캐시가 있어도 503 | 자동 테스트 |
| DB보다 큰 잘못된 캐시 번호 | 해당 캐시를 버리고 복구 | 자동 테스트 |

프로세스가 DB 저장 확정 직후 종료되면 다음 동일 거래 요청은 DB 응답을 반환하고, 다음 신규 거래는 DB 번호로 캐시 누락을 감지합니다. 이 중간 상태는 자동 테스트의 캐시 발행 실패로 확인합니다. 두 저장소의 정확한 사이에서 실제 프로세스를 강제로 종료하는 시험과 PostgreSQL 백업 복원 시험은 운영 단계에서 추가합니다.

## 실행하기 — cmd

Docker Desktop과 로컬 모델 파일을 준비하고 프로젝트 루트에서 실행합니다. 현재 사용 중인 API를 종료할 필요는 없습니다. 검증 도구가 임시 포트에서 별도 API 프로세스를 실행합니다.

```bat
cd /d D:\soyeon_project\fingaurd\finguard
docker compose up -d --wait postgres redis
uv run --env-file .env --locked --group api python tools/verify_score_api.py
```

`.env`의 `DATABASE_URL`, `REDIS_URL`, `SCORING_MODEL_PATH`를 읽습니다. DB 계정에 스키마 생성 권한이 필요합니다. 검증용 `verify_<무작위 값>` 스키마와 그 스키마에서 파생한 Redis 키만 생성·정리합니다. 개발 테이블을 지우거나 Redis 전체를 비우지 않습니다. PostgreSQL·Redis 컨테이너도 중지하지 않습니다. API 프로세스는 각각 `--workers 1`로 실행해 도구가 생성한 프로세스만 종료합니다.

기본 조건은 카드 4개, 카드당 사전 이력 32건, 모드별 준비 요청 4건과 측정 요청 64건, 동시 요청 4개입니다. DB 단독과 Redis 공유 모드 모두 독립 API 서버 2개를 사용합니다. 두 모드는 카드 ID를 분리하되 같은 시각·금액·업종·이력 건수로 맞춥니다.

다른 작업량으로 측정하려면 옵션을 지정합니다.

```bat
uv run --env-file .env --locked --group api python tools/verify_score_api.py --requests 256 --cards 8 --history-per-card 64 --concurrency 8 --output reports/score_api_larger
```

`--requests`, `--cards`, `--history-per-card`, `--concurrency`는 양수입니다. 기본 결과 파일은 `reports/score_api_verification.md`와 `.json`이며 성공한 실행만 새 보고서를 작성합니다. 기존 보고서는 같은 출력 경로로 재실행하면 덮어씁니다. 서버 로그는 Git에서 제외된 `.uv-cache/verify_*/`에 남습니다.

## 무엇을 비교하나

측정 요청의 HTTP 응답을 DB에 저장한 최초 응답과 비교합니다. 마지막에는 모든 검증 거래를 DB 확정 순서대로 메모리 계산기에 다시 넣고 점수·피처·조사 여부·군집·버전을 대조합니다. 점수 허용 차이는 `1e-7`이고 나머지 응답 값은 일치해야 합니다. 합성 거래를 사용하므로 사기 탐지 정확도나 재학습 성능을 평가하는 도구는 아닙니다. 외부 LLM 호출도 없습니다.

측정 결과와 해석은 [통합 검증 보고서](../reports/score_api_verification.md)에 있습니다. 응답 중앙값은 중간 응답 시간이며, p95는 응답 시간순으로 95% 위치의 값입니다. 준비 요청·서버 시작·사전 이력 저장은 측정에서 제외합니다. 개별 응답 시간은 클라이언트 작업 대기열에서 꺼낸 뒤부터 측정하고, 처리량은 모든 측정 요청을 마치는 전체 시간으로 계산합니다.

이번 작은 작업량의 한 번 측정에서는 Redis가 전반적으로 더 빠르다고 볼 수 없었습니다. 캐시는 최근 거래 목록 조회를 줄이지만 DB 연결·중복 확인·원본 저장·상태 직렬화 비용이 남습니다. 운영 성능을 판단하려면 더 큰 이력, 여러 실행 순서와 반복, 실제 환경의 부하 측정이 필요합니다. 이 최적화는 #23, 백업·복원과 운영 장애 검증은 #18에서 이어갑니다. 사건 생성 시 중복 방지는 #10의 사건 기능과 함께 검증합니다.
