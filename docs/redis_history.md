# Redis 카드 이력 공유와 복구

PostgreSQL에는 거래와 당시 판단 결과를 남깁니다. Redis에는 카드별 최근 이력의 복사본을 두어 여러 API 프로세스가 공유합니다. Redis가 없어지거나 연결되지 않으면 DB 기록으로 계산하고, 연결이 돌아온 뒤 새 거래를 처리할 때 캐시도 복구합니다.

## 실행하기 — Windows 명령 프롬프트(cmd)

Docker Desktop을 실행한 상태에서 프로젝트 폴더로 이동합니다.

```bat
cd /d D:\soyeon_project\fingaurd\finguard
if not exist .env copy .env.example .env
```

기존 `.env`가 있다면 `REDIS_URL=redis://127.0.0.1:6379/0`을 추가합니다. `DATABASE_URL`과 모델 경로도 기존 설정을 유지합니다. Redis만 설정하고 DB 주소를 비우면 API가 시작되지 않습니다.

```bat
docker compose up -d --wait postgres redis
docker compose ps
uv run --env-file .env --locked --group api python -m finguard.database
uv run --env-file .env --locked --group api uvicorn finguard.api:app --host 127.0.0.1 --port 8000 --workers 1
```

두 서비스가 `healthy`인지 확인하고, 브라우저에서 `http://127.0.0.1:8000/docs`를 엽니다. 이미 켜 둔 API는 그 터미널에서 `Ctrl+C`로 종료한 뒤 다시 실행해야 새 코드와 설정을 읽습니다. PowerShell에서는 첫 이동 명령을 `Set-Location 'D:\soyeon_project\fingaurd\finguard'`로 바꾸고 환경 파일 복사는 `if (-not (Test-Path .env)) { Copy-Item .env.example .env }`를 사용합니다.

## 저장 내용

Redis 키는 `finguard:history:v1:<DB 연결 설정 해시>:<카드 ID 해시>`입니다. API 프로세스들이 같은 DB 연결 설정과 Redis 주소를 사용하면 같은 이력을 공유합니다. 카드 ID를 키에 직접 넣지 않지만, 이 해시를 개인정보 암호화로 취급하지는 않습니다.

| 항목 | 의미 |
| --- | --- |
| `revision` | 해당 카드의 마지막 확정 거래 번호. PostgreSQL `sequence`와 비교함 |
| `state.snapshot_version` | 캐시 저장 형식 버전 |
| `state.feature_version` | 이력 계산 방식 버전 |
| `state.last_time` | 마지막 거래 시각 |
| `state.amounts` | 마지막 거래 시각 기준 최근 7일의 거래 시각·센트 단위 금액 |

금액은 정수 문자열로 보관합니다. 복원할 때 최근 1시간 건수, 최근 7일 건수·금액 합·제곱합을 구성하고 기존 계산기로 평균과 표준편차를 계산합니다. 학습 때와 같은 계산 규칙을 사용합니다.

키는 갱신 후 실제 시간 기준 7일이 지나면 만료됩니다. 탐지 이력의 1시간·7일 범위는 원본 거래 시각을 기준으로 계산하므로 키 만료 시간과 구분합니다. Redis 컨테이너에는 디스크 저장을 사용하지 않습니다. 재시작으로 캐시가 사라져도 DB에서 복구할 수 있습니다.

## 요청 처리

1. DB에서 거래 ID와 카드별 잠금을 잡습니다. 같은 ID·같은 내용이면 저장한 최초 응답을 반환하고 캐시를 증가시키지 않습니다.
2. 해당 카드의 DB 마지막 거래 번호를 확인합니다. 캐시 번호·마지막 시각·형식·피처 버전이 맞으면 캐시를 사용합니다.
3. 캐시가 없거나 맞지 않으면 DB의 직전 7일 거래를 시간·처리 순서대로 읽어 이력을 만듭니다. 이 복구는 저장된 거래를 다시 계산하는 뜻이며, 점수 API로 거래를 다시 전송하거나 원본을 중복 저장하지 않습니다.
4. 현재 거래의 직전 이력으로 점수를 계산하고 DB에 거래·응답을 함께 확정합니다.
5. 확정된 거래까지 포함한 새 이력을 Redis에 반영합니다. 번호·이력·만료 시간을 Lua 스크립트 한 번으로 갱신합니다.

동일 카드 요청은 DB 잠금으로 순서화합니다. Redis에는 큰 거래 번호가 이미 있으면 작은 번호의 뒤늦은 갱신을 거부하도록 했습니다. DB 저장 직후 다른 요청이 먼저 끝나더라도 최신 이력을 덮어쓰지 않습니다. 거래 번호는 문자열로 비교해 큰 정수의 실수 반올림을 피합니다.

## 장애별 동작

| 상황 | 처리 |
| --- | --- |
| 캐시 정상 | 최근 거래 목록 DB 조회를 생략하고 캐시 이력을 사용 |
| 캐시 유실·만료·형식 손상·구버전 | DB로 계산하고 성공한 신규 거래 뒤 캐시를 복구 |
| Redis 연결 실패 | DB로 점수를 계산하고 저장. Redis 연결 시도는 읽기·쓰기별로 발생할 수 있음 |
| DB 성공 후 Redis 쓰기 실패 | API는 저장된 결과를 반환. 다음 신규 거래에서 DB 번호 불일치를 감지해 복구 |
| DB 확정 직후 프로세스 종료 | 같은 거래 재요청은 DB 응답 반환. 캐시는 다음 신규 거래에서 복구 |
| 모델·DB INSERT·최종 COMMIT 실패 | 503 반환. 새 Redis 이력을 발행하지 않음 |
| PostgreSQL 장애 | 503 반환. 캐시만으로 거래를 승인하거나 기록하지 않음 |
| 같은 ID의 내용 변경 또는 늦은 과거 거래 | 기존 409 처리 유지 |

Redis 연결·응답 대기 시간은 각각 0.25초이고 자동 재시도는 끕니다. Redis 장애 자체로 거래를 잃지 않지만, DB 장애 시에는 저장할 수 없어 요청이 실패합니다. Redis 키·값의 읽기 및 쓰기 실패는 연결 주소 없이 서버 로그에 남깁니다.

DB와 Redis는 별도로 저장합니다. API 시작 시 전체 카드를 미리 복구하지 않고 새 거래가 들어온 카드부터 복구합니다. 모델·정책 버전과 원래 점수는 DB 응답에 남고, 피처 버전은 DB 응답과 캐시에 남습니다. `REDIS_URL`을 비우면 DB만 사용하는 모드로 돌아갑니다. DB 연결 문자열을 바꾸면 캐시 키도 달라지고 DB에서 새로 구성합니다.

## 검증

개발 거래를 지우지 않도록 테스트별 DB 스키마와 그에 대응하는 Redis 키를 사용합니다. Redis 전체 삭제 명령은 사용하지 않습니다. cmd에서 테스트하려면 다음을 실행합니다.

```bat
set TEST_DATABASE_URL=postgresql://finguard:finguard_local@127.0.0.1:5432/finguard
set TEST_REDIS_URL=redis://127.0.0.1:6379/0
uv run --locked --group api pytest -q -W error
```

로컬 Docker PostgreSQL 17·Redis 7에서 전체 테스트 44개를 통과했습니다. 서로 다른 캐시 클라이언트의 이력 공유와 최근 거래 DB 조회 생략, 캐시 유실·손상·접속 장애, DB 확정 후 발행 실패, 모델·INSERT·COMMIT 실패, 동시 중복·동일 카드 요청, 큰 거래 번호의 순서 비교, 시간 경계·소수 정밀도, API 재시작을 확인했습니다. DB보다 큰 잘못된 캐시 번호도 버리고 복구하는지 검증했습니다. GitHub Actions에도 두 저장소를 연결한 동일 검사를 추가했습니다.

실제 저장 모델과 Uvicorn에서도 거래 4건의 점수·이력이 메모리 모드와 일치했습니다. API 재시작 후 중복 응답을 유지하고, 해당 카드의 캐시를 지운 뒤 DB에서 다시 구성하는 흐름도 확인했습니다.

요청마다 DB의 중복·마지막 거래 번호 확인은 계속 수행하며, 캐시 상태 직렬화·복원 비용도 있습니다. 처리량이나 지연 시간이 개선됐다고 판단하려면 별도 부하 측정이 필요합니다. 사건 생성 기능은 아직 없으므로 사건 중복 방지는 그 기능과 함께 검증합니다.
