# 거래 API 통합 검증과 로컬 성능 기준선

측정 시각: 2026-11-19T23:06:29.987273+09:00

## 측정 조건

- Python 3.12.13 / Windows 11
- PostgreSQL 17.12 (Debian 17.12-1.pgdg13+1) / Redis 7.4.12
- 모델 SHA-256: `aef236bf79b8d4937c862ad22277336cb9f2b52044941f36692ad5d1f77d23bf`
- 피처 버전: `1` / 정책 버전: `fixed-threshold-v1`
- 카드 4개, 카드당 사전 이력 32건과 준비 요청 1건
- 모드별 독립 API 프로세스 2개, 같은 모델·요청 수·동시 요청 수
- 금액 10.00·동일 시각·동일 업종의 합성 거래. 실제 사기 탐지 정확도 평가는 포함하지 않음

## 응답 시간

| 모드 | 성공/요청 | 동시 요청 | 처리량(건/초) | 중앙값(ms) | p95(ms) | 최대(ms) |
| --- | --- | --- | --- | --- | --- | --- |
| postgres_only | 64/64 | 4 | 74.94 | 50.55 | 67.99 | 77.92 |
| redis_shared | 64/64 | 4 | 71.86 | 48.7 | 89.3 | 104.02 |

처리량은 측정 요청 수를 전체 실행 시간으로 나눈 값이다. 중앙값은 중간 응답 시간이고, p95는 응답 시간순으로 95% 위치에 해당하는 값이다. 클라이언트 작업 대기열에 머문 시간은 개별 응답 시간에 포함하지 않는다. 준비 요청과 모델 시작 시간도 측정에서 제외했다.

## 정합성과 복구

- DB 확정 순서로 395건을 다시 계산해 점수·피처·판단·버전이 일치함
- 두 API 프로세스에 같은 거래를 동시에 8번 보내도 DB에 한 건만 추가됨
- 같은 ID의 내용 변경은 409, 잘못된 금액은 422, 늦은 과거 거래는 409임
- Redis 접속 불가 상태에서도 DB에 거래를 저장하고 같은 요청의 최초 응답을 반환함
- API 재시작 후 최초 응답이 유지되고, 캐시 유실 후 신규 거래에서 DB로 복구함
- 외부 LLM 호출 없이 실행함. 개발 거래와 다른 DB 스키마·Redis 키를 사용 후 정리함

## 해석 범위

이번 결과는 로컬의 작은 합성 작업량을 한 번 측정한 기준선이다. 모드 실행 순서는 DB 단독, Redis 공유 순서이며 서버 부하·DB 연결·운영체제 캐시의 영향을 받는다. Redis를 사용해도 중복 확인·최신 거래 조회·DB 저장과 이력 직렬화 비용은 남는다. 이 수치로 운영 처리량이나 Redis의 일반적인 성능 우위를 단정하지 않는다. 큰 이력·여러 반복·실제 환경의 부하 시험은 후속 작업이다.
